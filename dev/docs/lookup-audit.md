# Lookup-table audit

Audit only: this records repeated database text and recommendations. It makes no schema or data changes. Reviewed
`dev/database/backupsqlmigration.sql` and the current faculty, registrar, and shared grade/section callers.

| Table and column | Repeated value example | What a typo or rename can break | Recommendation |
| --- | --- | --- | --- |
| `sections.academic_year`, `enrollments.school_year`, `academic_history.school_year`, `promotion_logs.school_year`, and `grading_scales.school_year` | `2024-2025`, `2025-2026`, `2026-2027` | Exact filters and joins can split one school year into multiple values. Grades can appear missing, promotion checks can miss records, or year-specific settings/scales can fail to load. `school_year_settings.school_year` is already a primary key, but settings are not a complete year catalog and the other columns do not reference it. | Add a dedicated school-year lookup and reference it from operational tables. Keep a year snapshot on immutable historical records if preserving the original label is important. |
| `academic_history.subject` vs. `subjects.subject_name` | `Practical Research 1` appears in the subject-rename migration | Faculty grade lookup, correction, and lock operations compare subject names exactly. A renamed catalog entry can make existing grades appear missing unless history is updated too; v27 explicitly renamed both. | Do not replace the historical subject text outright. For newly managed grades, add a stable `subject_id` relation while retaining the displayed subject snapshot for legacy/history rows. |
| `admission_applications.grade_level` vs. numeric grade fields in `students`, `sections`, `enrollments`, and `grade_levels` | `Grade 7`, `7`, and `Kindergarten` are accepted representations | Free-text values can fail conversion or be treated differently by filters. The migration's `grade_number()` parser has to normalize these spellings before comparing them with numeric grades. | Normalize new applications to a numeric grade-level key. Keep the original submitted label only if needed for the historical application record. |
| `subject_schedules.faculty_name` vs. `staff_profiles` | A teacher name can be repeated across that teacher's schedule rows | Name spelling/spacing differences can prevent schedule ownership checks and notifications from matching. The newer `faculty_profile_id` relation already provides a stable staff reference. | Use `faculty_profile_id` for active schedule relationships; retain the name only as a historical/display snapshot until old schedule data is verified. |
| `sections.section_name` | A section label such as `Masunurin` | The audit found `section_id` references in enrollments and subject schedules rather than a second core `section_name` column. Notification text may contain a copied label, but it is a historical message. | Keep `sections.section_name` as the catalog value; do not normalize stored notification text. No additional core-table copy was found in the reviewed schema. |
| `grade_levels.grade_level` and grade fields on students, sections, and enrollments | Integer grade `7` | These fields can disagree if a row uses a different numeric grade, but they do not repeat a free-text label. The shared grade-level table and application logic already use numeric values. | Keep numeric grades and the existing grade-level catalog. Avoid adding duplicated grade-label text columns. |

This is a review for a lead decision, not an instruction to migrate existing data. In particular, historical values should
not be rewritten until the retention and reporting effects are checked.
